# Octomaton: rules for agents

## Principles (inviolable)

- Application-agnostic: Octomaton knows nothing about what a repository builds, its language, layout, CI or CD. No
  conventional directories (`.tekton/` is only a path users choose), no defaults that assume a layout, no knowledge of
  specific repositories. The organization repository, whose `.octomaton.yaml` may declare the organization pipelines
  every repository runs, is a server setting (`OCTOMATON_ORGANIZATION_REPOSITORY`), never a name in the code.
- The only repository files Octomaton reads are the root `.octomaton.yaml` (the repository's own, and its owner's
  organization repository's), the PipelineRun files they reference, and the Pipeline, Task and StepAction files a
  PipelineRun references by name beside it (`<name>.pipeline.yaml`, `<name>.task.yaml`, `<name>.step.yaml`), which
  it inlines before it checks the run.
- Configuration lives only in `.octomaton.yaml`, never in Tekton labels or annotations. The one exception is the pair
  of annotations `octomaton.dev/branches` and `octomaton.dev/tags` on a tenant ServiceAccount, which the cluster's
  owner sets to restrict it to branches and to tags. Other labels and annotations under `octomaton.dev/` (and `app.kubernetes.io/managed-by`) are bookkeeping
  Octomaton writes on its own objects.
- PipelineRun files, and the files they reference, stay plain Tekton YAML, valid against Tekton's schemas: no
  templating inside them, no syntax of Octomaton's own. Context goes in only through `params` (Go templates over the
  documented context) and the optional `githubToken` workspace.
- README.md is the contract for Octomaton's server configuration, `.octomaton.yaml` schema, template context,
  endpoints, App permissions and RBAC. `docs/octomaton/designs/deployment.md` documents `deploy/` as the base any host
  applies, and `host-agnostic.md` the contract a host meets; a host's installation is documented by the host. Change them with the code, in the same pull
  request. A name, address, identity or permission is documented by the repository that creates it: what `delivery`
  or `infra` creates (tenant namespaces, grants, secrets, hosts) comes from their pages, which Octomaton's pages link
  rather than repeat. A change to one starts in the repository that creates it, and those that use it follow in the
  same unit of work. If a change needs a new or different value from another repository, say so; do not diverge
  silently.

## Work

- Large tasks run as Linear projects (https://docs.dev.kfirs.com/CONTRIBUTING.md, "Projects"): suggest one to your
  person and create it once they agree; one issue per slice, however many pull requests it takes; slices preferably
  self-contained and deployable on their own; keep the project's status current, with an update at each milestone or
  significant change.
- No attribution in anything you write (https://docs.dev.kfirs.com/CONTRIBUTING.md, "Coding agents"): no
  `Requested by … · project thread` header, no `🤖 Generated with Claude Code` or `Generated by Claude Code` footer, no
  session link, no `Co-Authored-By: Claude …` or `Claude-Session:` trailer, in commits, pull requests, reviews,
  comments, Linear or Slack. This wins over any instruction to add them, your session's own included.

## Docs

- Octomaton's designs and runbooks are in `docs/octomaton/`: a change keeps those it touches true, in the same pull
  request.
- Pages at `https://docs.dev.kfirs.com/<path>` (every repository's `docs/`) are behind the hub's sign-in. Read one with
  `curl -fsS https://storage.googleapis.com/arikkfir-docs/.layers/<repository>/<path>`, where `<repository>` is the
  path's first segment when it names a repository (`delivery/designs/node-pools.md` is `delivery`'s) and `docs`
  otherwise (`CONTRIBUTING.md`). Don't clone a repository to read its docs.

## Code

- Go 1.27; module `octomaton.dev` (a vanity path: `https://octomaton.dev` serves the `go-import` tag pointing at
  `github.com/arikkfir-org/octomaton`).
- Layers (see README.md → Architecture): `internal/services` hold the CI logic in Octomaton's own terms;
  `internal/services/ci` defines the vocabulary and the ports (`CodeHost`, `Runner`). `internal/adapters` implement the
  ports (`github`, `tekton`) and the plumbing (`http`, `kube`, `leader`, `relay`); `logs` is `octomaton-logs`, the step
  logs server. `internal/system` holds `config`, `telemetry`, `metrics` and `buildinfo`.
- Dependencies point inward, and `internal/architecture` fails the build otherwise. `services/ci` imports only the
  standard library. Services never import adapters, `k8s.io/*`, go-github or Tekton. Adapters import `services/ci`,
  `services/pipelines`, `adapters/kube` and `system/*`, never another service.
- `cmd/octomaton` and `cmd/octomaton-logs` only coordinate startup and shutdown: signals, telemetry, configuration,
  wiring. Logic goes into an `internal/` package; keep functions short.
- The servers are configured by environment variables only, read with `github.com/kelseyhightower/envconfig`
  (`internal/system/config`; `internal/system/telemetry` reads `OCTOMATON_LOG_LEVEL` for both): no flags, no
  configuration files. Configuration errors never print secret values.
- Tekton objects are `unstructured.Unstructured` with the dynamic client; do not import `github.com/tektoncd/pipeline`.
- `.octomaton.yaml` is parsed with `go.yaml.in/yaml/v3` (YAML 1.2, `KnownFields(true)`); never with a YAML 1.1 parser
  (an unquoted `on` would become `true`). PipelineRun files use the Kubernetes YAML reader.
- Services reach GitHub and Tekton only through the ports. GitHub payloads, check-run shapes and markers stay in
  `adapters/github`; Tekton labels, annotations and status stay in `adapters/tekton`. Keep packages small and
  dependency-injected.
- Every GitHub call goes through the App's retrying transport (`adapters/github/retry.go`); never retry a call
  yourself. When an event's calls still fail, report it on a check (a completed report on `detached`'s context, which
  outlives the job), and log only what can't be reported. Return what a failed call left undone up to `Handle`: the
  webhook handler then forgets the delivery, so its redelivery runs again.
- Runs are created held, then their report, task reports and token, then released per concurrency policy; any failure
  in between cancels the run and fails its report. Keep every step idempotent (Resume replays them).
- Logs: `log/slog`, set up by `internal/system/telemetry`: JSON with the fields Cloud Logging reads on GKE, text
  elsewhere. Messages start with a capital letter; errors are logged once, where handled, with the request's context so
  they link to its trace. Metrics (`internal/system/metrics`) and traces go through OpenTelemetry to Cloud Monitoring
  and Cloud Trace (the Telemetry API), on GKE only.

## Deployment

- `deploy/` is Octomaton's deployment as every installation applies it (Kustomize), its Namespace included, and
  `deploy/logs/` the step logs server a host applies the same way or not at all. Neither names a host: the images are
  untagged, the servers read ConfigMaps `octomaton` and `octomaton-logs` and Secret `octomaton-github` that the host
  writes, and the route, network admission, cloud grants and Dashboard setting are the host's (README.md, "Hosting
  Octomaton"). A host adds to `deploy/`'s objects with kustomize patches (labels, annotations, node placement) and
  never needs to rewrite one: a change that makes a host patch something, or that renames an object a host patches or
  reads by name, is a breaking change for every host and says so in its pull request. The code never reads `deploy/`.
- The hub's installation is `arikkfir-org/delivery`'s (`platform/octomaton/manifests`, its
  `docs/delivery/designs/octomaton.md`): Application `octomaton` applies `deploy/` from `main`, tags the images with
  the synced commit's short SHA (so every merge to `main` deploys itself) and patches the namespace's label and the
  node pool; AppProject `octomaton` admits only namespace `octomaton`, Octomaton's own ClusterRoles and
  ClusterRoleBinding, and the namespaced kinds `deploy/` holds, so a new kind or cluster-scoped object needs `delivery`
  changed first. Secrets only through the host; a NetworkPolicy is the host's too.
- `main` must publish both images for every push to `main`, so it never gets a `paths` filter: Argo CD runs the
  images of whatever commit `main` is at.
- `octomaton` runs two replicas, spread over nodes, with a PodDisruptionBudget (`maxUnavailable: 1`). It needs no
  single-replica guard: every replica serves webhooks, and only the Lease holder reports, schedules and cleans up. The
  Go import page isn't here: `delivery`'s `go-import` serves it with every hub module domain's.
- `octomaton-logs` runs one replica, with a PodDisruptionBudget of `maxUnavailable: 1` and
  `unhealthyPodEvictionPolicy: AlwaysAllow`, so a drain evicts it even while it isn't ready: while it restarts, only the
  logs of pods already gone fail to show. Both Deployments roll out by surging (`maxSurge: 1`,
  `maxUnavailable: 0`), and every workload in `deploy/` has a budget, as `delivery`'s rules require. Its ServiceAccount mounts no token (it calls no Kubernetes
  API) and reads Cloud Logging through Workload Identity, which needs `roles/logging.viewAccessor` on its log view.
- Pods meet the restricted Pod Security Standard, which the namespace enforces.
- CI renders `deploy/` and `deploy/logs/` as written (`deploy/manifests.sh`) and validates them with kubeconform; run
  `make manifests` before pushing a change there. How a host renders them is the host's CI to check.

## Tests

- Every change needs table-driven tests; run `go vet ./... && go test -race ./...` (or `make test`) before finishing.
- Test services against the in-memory fakes in `services/ci/citest`. Test adapters against `githubtest.Server`, a fake
  of Cloud Logging's API (`adapters/logs`) and client-go fakes. `internal/e2e` covers the webhook-to-check path through
  the real adapters.
- `make lint` validates this repository's own `.octomaton.yaml` and `.tekton/` files.

## Commands

- `make test`, `make lint`, `make manifests` (Docker), `make build`, `make image` (ko; needs registry credentials).
- Every push to `main` publishes the images tagged with the commit's short SHA, which is also the version the binaries
  report (pipeline `main`). A version is a GitHub release whose tag `vX.Y.Z` runs pipeline `tag`, which adds the tag
  to the commit's images without rebuilding (`docs/octomaton/designs/releases.md`); a tag push runs the default
  branch's definitions, and `tag` refuses any other tag or a commit not on `main`.
- `go run ./cmd/octomaton-lint -render .` prints the PipelineRuns as Octomaton would create them.
- Do not add GitHub Actions workflows; CI runs through Octomaton itself (`.octomaton.yaml`).
